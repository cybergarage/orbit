# Recovery and completion follow-up: 2026-09-25

This experiment changes the evaluation agent's instructions and records the
outcomes. It does not change Orbit's product prompts, public APIs, authorization
errors or default runtime limits. Source baseline: `a7e912ddbe3d0aeb2f4db601dc167d3bb8a2b3d3`,
with the test-host changes uncommitted at evaluation time. The existing agent images
were reused because their worker and Orbit production source did not change.

## What changed and why

| Observation                                                             | Implemented change                                                          | Intended effect                                               |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Agents tried unavailable `python` and absent Git history                | State `python3` and the snapshot's lack of Git history before solving       | Avoid environment discovery failures                          |
| Gemma repeated an exact-text edit whose quotes did not match            | Read relevant code first; re-read and rebuild an edit after failure         | Recover using the actual current file                         |
| The previous SWE patch passed, but the agent kept requesting more tests | Request focused regression checks and a final summary once those pass       | Finish without unnecessary further tool calls                 |
| Deadline records alone did not explain delays                           | Record model/tool counts, Ollama timing components and host timeout overrun | Separate observations about inference, tools and host control |

The strategy is named `coding-recovery-v1`. `ORBIT_E2E_STRATEGY=baseline` preserves
the original instructions for a control run. No problem solution or hidden grading
information was added to the prompt. The small-case grader and fixtures are
unchanged. The improvements above were tested together; this experiment does not
isolate the contribution of each instruction.

## Small cases: all 24 trials passed at the original limit

Both models ran all four cases three times, with the original 12-tool-iteration
limit and 240-second Run budget. The successful trials all completed normally
and passed independent checks; neither model needed a larger budget.

| Model         | Previous resolved / 12 | Improved resolved / 12 | Improved timeouts |
| ------------- | ---------------------: | ---------------------: | ----------------: |
| gemma4:12b    |                      8 |                     12 |                 0 |
| ornith-1.5:9b |                      9 |                     12 |                 0 |

The multi-file case improved from Gemma 0/3 and Ornith 1/3 to 3/3 for both.
Gemma used nine tool calls on each improved multi-file trial. Its edits succeeded;
it ran a failing test, fixed one file, observed the remaining failure, fixed the
other file, and reran successfully. Those intermediate test failures are useful
feedback, not repeated invalid edits. Ornith used 9, 9 and 10 calls with no tool
errors for this case.

Improved totals were 334.0 wall seconds / 88623 input tokens / 4640 output tokens
for Gemma and 436.0 seconds / 147250 input tokens / 9353 output tokens for Ornith.
All improved small-run usage records were complete. The previous run included
interruptions and incomplete usage, so aggregate time/token differences cannot
be attributed solely to the instructions. In particular, input totals include
repeated context and are not unique prompt sizes.

The previous and new runs are successive experiments, not interleaved randomized
controls. Host conditions differed, and three repetitions are too few for a
general reliability claim. No host timeout occurred in the new matrix; this does
not establish the cause of the old timeouts. Some older provider timing fields
also disagree with their recorded total durations, so those values are retained
as diagnostics rather than used for a throughput conclusion.

Artifacts: `tmp/e2e/runs/2026-09-25T00-14-56.771Z-small`.
[The comparison JSON](2026-09-25-recovery-small.json) contains the new environment,
all 24 outcomes, and baseline metrics derived from the retained old event files.
The old raw records were not rewritten.

## SWE-bench: 30 versus 50 tool iterations

The same `sympy__sympy-20590` problem is evaluated with ornith-1.5:9b, thinking
disabled, context 32768, temperature 0.6, top-p 0.95, seed 42 and a 900-second
Run budget. Only the iteration budget changes between the new attempts. Both
receive identical improved prompts; independent official grading checks each
submitted patch. The original reference-patch verification is retained.

| Instructions                  | Limit | Actual tool calls | Wall seconds | Runtime outcome | Official disposition                           |
| ----------------------------- | ----: | ----------------: | -----------: | --------------- | ---------------------------------------------- |
| Recovery v1                   |    30 |                30 |        135.1 | budget-exceeded | empty patch; not executed                      |
| Recovery v1                   |    50 |                50 |        272.8 | budget-exceeded | empty patch; not executed                      |
| Original (additional control) |    50 |                41 |        320.1 | completed       | resolved: 1/1 FAIL_TO_PASS, 21/21 PASS_TO_PASS |

The recovery prompts have identical SHA-256 hashes. The model digest, archive,
generation settings and time budget were also equal. Increasing the limit for
that strategy consumed more time and tokens without producing a patch. The
recorded usage was 156120/2633 input/output tokens at 30 and 369785/5469 at 50;
those budget-stopped usage records are conservatively marked incomplete.

An additional control used the original prompt at 50. Its prompt hash matches
the historical original-prompt run at 30, which produced a passing patch but
stopped at the iteration limit. The new control edited the file on its 25th tool
call, performed further checks and finished normally after 41 calls. It used
532627 input / 5261 output tokens with complete usage accounting. Official run
`orbit-prediction-c965131d-6b17-43fe-be2c-9c9c61802662` accepted the patch and passed
all 22 evaluation tests. The patch retains generated `.pytest_cache` data exactly
as submitted; no human correction or cache filtering was performed.

These are one attempt per new SWE condition, with a historical baseline-30
comparison. Fixed seeds do not guarantee identical trajectories. The result does
not establish a general causal benefit or an optimal budget, and the extra
verification costs time and tokens. It does demonstrate one clean completion
with the tested original-prompt/50/think-false configuration.

[The SWE comparison JSON](2026-09-25-recovery-swe.json) records all three attempts,
including the failures, official dispositions, settings and equality checks.
[The successful submitted JSONL](2026-09-25-baseline50-predictions.jsonl) can be
regraded with the same prepared official harness.

## Adopted settings and remaining work

- **Small E2E: adopt recovery v1, keep 12 iterations and thinking disabled.** All
  24 trials passed, including the previously failing multi-file cases.
- **SWE evaluation: retain the original prompt, select 50 iterations and thinking
  disabled as the default tested configuration.** The recovery prompt remains
  explicitly selectable for experiments, but is not adopted for SWE. The
  900-second time budget is unchanged; the iteration cap is not removed.
- **Orbit product defaults: unchanged.** This evidence concerns evaluation-host
  settings, not a universal budget for every Agent or application.
- Further work should separate environment, edit-recovery and completion
  instructions into controlled experiments across more problems. A generic
  instruction that helped the small fixtures did not transfer to this SWE task.
  Do not treat all tool errors as framework defects: grep with no matches and
  investigative Python exceptions also contribute to that diagnostic count.
